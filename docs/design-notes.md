# Design Notes

## 1. Overview

`ops-scheduler-batch-jobs`는  
운영 환경에서 사용되던 스케줄러 기반 배치 작업 구조를  
포트폴리오 목적에 맞게 재구성한 프로젝트입니다.

이 문서는 해당 구조를 선택한 이유와  
주요 설계 판단을 정리한 문서입니다.

<br/>

## 2. Why a Scheduler-based Batch Structure Was Needed

운영 환경에서는 정해진 주기마다 외부 데이터를 조회하고,  
필요한 형식으로 가공한 뒤 저장하거나 후속 처리에 활용하는 작업이 필요했습니다.

이런 작업은 단순 API 요청/응답 구조와 다르게  
다음과 같은 특성을 가집니다.

- 정해진 시간 또는 주기 기반 실행
- 외부 연동 실패 가능성 존재
- 반복 대상 루프 처리 필요
- 결과 저장 및 후속 확인 필요
- 실행 이력과 상태 가시성 중요

따라서 단순한 스케줄 메서드 호출이 아니라,  
실행 제어 / 외부 연동 / 정규화 / 저장 책임을 나눈  
배치 구조가 필요하다고 판단했습니다.

<br/>

## 3. Why Execution Control Was Important

배치 작업은 정상 동작보다도  
**중복 실행되지 않는 것**, **실패 시 통제 가능한 것**, **운영자가 확인 가능한 것**이 중요합니다.

특히 서버 이중화 환경에서는  
같은 스케줄이 여러 인스턴스에서 동시에 실행될 수 있기 때문에  
실행 제어 전략이 반드시 필요합니다.

이 프로젝트에서는 다음 관점을 중요하게 보았습니다.

- 동일 작업의 중복 실행 방지
- 배치 실행 시점 분산
- 외부 연동 실패 시 재시도 가능성 확보
- 최소한의 운영 확인 수단 제공

<br/>

## 4. Why Group-based Distributed Scheduling Was Chosen

이 프로젝트에서는 이중화 환경에서의 중복 실행 위험을 줄이기 위해  
서버 그룹별 시간 분산 실행 구조를 적용했습니다.

예를 들어 다음과 같은 방식입니다.

- Group A: 0 / 6 / 12 / 18 시 실행
- Group B: 3 / 9 / 15 / 21 시 실행

이 방식의 목적은  
모든 서버가 같은 시점에 동일 배치를 동시에 수행하는 상황을 줄이는 것입니다.

즉, 이 구조는 완전한 분산 락 시스템을 구현하기 위한 것이 아니라,  
운영 환경에서 스케줄 충돌 가능성을 낮추기 위한  
기본적인 실행 분산 전략을 설명하는 데 목적이 있습니다.

<br/>

## 5. Why Responsibility Was Separated

배치 구조를 하나의 Scheduler 내부에 모두 넣으면  
실행 제어, 외부 연동, 데이터 변환, 저장 로직이 혼합되어  
유지보수와 테스트가 어려워질 수 있습니다.

그래서 본 프로젝트에서는 다음과 같이 책임을 분리했습니다.

- `Scheduler`
  - 실행 트리거 및 그룹 분기 담당

- `InquiryService`
  - 조회 대상 반복 처리 및 전체 흐름 조정

- `StoreClient`
  - 외부 시스템 조회 책임 담당

- `FormService`
  - 외부 응답 데이터를 내부 표준 형식으로 정규화

- `Repository`
  - 결과 저장 및 조회 담당

이 구조를 통해 각 계층의 역할을 분명히 하고,  
외부 연동이나 저장소 구현이 변경되어도 전체 흐름을 크게 흔들지 않도록 했습니다.

<br/>

## 6. Why Retry with Backoff Was Considered

외부 연동은 항상 성공한다고 가정할 수 없기 때문에  
실패 시 재시도 구조를 고려하는 것이 필요했습니다.

단, 연속적인 즉시 재시도는  
외부 시스템과 내부 시스템 모두에 부담이 될 수 있으므로  
일정 간격 또는 Backoff 개념을 적용하는 방향이 더 적절하다고 판단했습니다.

이 구조를 통해 기대한 점은 다음과 같습니다.

- 일시적 실패에 대한 복원력 확보
- 즉시 실패로 끝나는 흐름 완화
- 외부 시스템 부하 완화
- 운영 중 재처리 가능성 확보

즉, 재시도는 단순 예외 보완이 아니라  
배치 구조의 복원력을 높이기 위한 설계 요소로 보았습니다.

<br/>

## 7. Why Lock Was Added

배치 실행 제어에서 중요한 것은  
같은 작업이 동시에 중복 실행되지 않도록 하는 것입니다.

포트폴리오에서는 InMemory Lock을 사용해  
기본적인 중복 실행 방지 구조를 재현했습니다.

이 방식은 단일 인스턴스 기준에서는 단순하고 이해하기 쉽지만,  
실제 운영 환경에서는 다음과 같은 확장이 필요할 수 있습니다.

- Redis 기반 distributed lock
- DB lock
- execution ownership 관리
- 실행 상태 테이블 기반 제어

즉, 본 프로젝트의 Lock은 완전한 운영 구현이라기보다  
**중복 실행 제어가 왜 필요한지**를 구조적으로 설명하기 위한 설계 요소입니다.

<br/>

## 8. Why Operational Visibility Was Included

배치 작업은 실행이 끝난 뒤  
운영자가 무엇이 처리되었는지 확인할 수 있어야 합니다.

코드가 잘 동작하는 것만으로는 부족하고,  
운영 관점에서는 아래가 중요합니다.

- 지금 실행되었는지
- 어떤 결과가 저장되었는지
- 특정 대상이 조회되었는지
- 실패 후 재확인이 가능한지

그래서 본 프로젝트에서는  
최소한의 운영 확인 API를 제공하도록 구성했습니다.

- 수동 1회 실행
- 최근 저장 결과 조회
- 단건 조회

이는 실제 운영용 Admin 시스템 전체를 구현한 것은 아니지만,  
배치가 “보이게 운영되어야 한다”는 관점을 반영한 것입니다.

<br/>

## 9. Why This Project Was Reconstructed as a Portfolio

이 프로젝트는 실제 운영 환경에서 사용되던  
스케줄러 기반 배치 구조를 포트폴리오 목적에 맞게 재구성한 것입니다.

실무에서는 외부 시스템 조회, 형식 정규화, 저장, 스케줄 실행 제어 등  
운영성 중심의 요구사항이 중요했습니다.

다만 포트폴리오에서는 다음 제약을 고려해야 했습니다.

- 실제 외부 연동 키/계정 정보 비공개
- 운영 환경 구성 정보 비공개
- 실제 저장소 및 연동 시스템 대체 필요

따라서 본 프로젝트는  
Mock Client, InMemory Repository를 사용해  
실제 운영 구조의 핵심 책임과 흐름만 남기는 방향으로 정리했습니다.

즉, 이 프로젝트의 핵심은 외부 스토어 연동 구현 자체보다  
**운영형 배치 구조와 책임 분리 방식**을 보여주는 데 있습니다.

<br/>

## 10. Summary

이 프로젝트의 핵심 설계 방향은 다음과 같습니다.

- 스케줄러 기반 배치 작업을 실행 제어 중심으로 구조화
- 그룹별 시간 분산 실행을 통한 중복 실행 위험 완화
- Scheduler / Inquiry / Client / Form / Repository 책임 분리
- 재시도(Backoff) 구조를 통한 실패 대응 고려
- Lock과 운영 확인 API를 통한 운영성 반영

이를 통해 `ops-scheduler-batch-jobs`는  
단순 스케줄 예제가 아니라,  
운영 환경에서의 실행 제어와 책임 분리를 고려한  
배치 구조를 정리한 포트폴리오로 구성되었습니다.
